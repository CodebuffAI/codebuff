# S4 — agent-runtime: tools/handlers

**Scope read:** `packages/agent-runtime/src/tools/handlers/list.ts` and the requested handlers under `packages/agent-runtime/src/tools/handlers/tool/` for `read_files`, `read_outline`, `str_replace`, `write_file`, `edit_transaction`, `apply_patch`, `code_search`, `glob`, `list_directory`, `query_index`, `run_terminal_command`, `check_job`, `kill_job`, `read_logs`, and `git_status`; corresponding schemas in `common/src/tools/params/tool/*`; SDK client implementations in `sdk/src/tools/*`; background job utilities.

**Audit domains covered:**
1. Path traversal / project-boundary enforcement
2. Schema ↔ handler/client drift
3. AbortSignal / cancellation propagation
4. Background job lifecycle and output-offset semantics
5. Async ordering / state mutation between handlers
6. Error handling and observability
7. Resource lifecycle / child-process cleanup / memory bounds
8. Tests/docs/contracts alignment

## [HIGH] security — `sdk/src/run.ts:827` — `run_terminal_command.cwd` can escape the project root
- **Risk:** The runtime advertises terminal commands as executing from the project root, but the SDK resolves a tool-supplied `cwd` with `path.resolve(projectRoot, terminalInput.cwd ?? '.')` and passes the result directly to `runTerminalCommand`. A payload such as `cwd: '../../..'` can run shell commands outside the project with the client process environment. This bypasses the project-boundary protections present on file tools and lets an agent read or mutate arbitrary host paths through the shell without any containment check.
- **Fix:** Resolve `terminalInput.cwd` through the same project-containment helper used by file tools (`resolveFilePathWithinProject`, including realpath/symlink checks), and return a structured error when the cwd is outside the project. Apply the same check before both SYNC and BACKGROUND command starts; add regression tests for `..`, absolute outside paths, sibling-prefix paths, and symlinked directories.
- **Evidence:** `sdk/src/run.ts:827-833` computes `const resolvedCwd = requireCwd(...)` then calls `runTerminalCommand({ ...terminalInput, cwd: path.resolve(resolvedCwd, terminalInput.cwd ?? '.'), env })` with no containment check. `sdk/src/tools/run-terminal-command.ts:158` starts BACKGROUND jobs with `cwd: path.resolve(cwd)`, and `sdk/src/tools/run-terminal-command.ts:199-205` spawns SYNC commands in `resolvedCwd`. By contrast, `sdk/src/tools/path-utils.ts:53-82` provides lexical + realpath project containment, and `sdk/src/tools/list-directory.ts:15-32` already uses it.

## [MEDIUM] correctness — `packages/agent-runtime/src/tools/handlers/tool/check-job.ts:23` — `kill_on_timeout` is accepted by schema and SDK but dropped by the runtime handler
- **Risk:** The public `check_job` schema documents `kill_on_timeout: false` as the way to keep a background job alive when a follow timeout expires. The agent-runtime handler constructs a narrower client call and omits that field, so every runtime-originated `check_job` follow call falls back to the SDK default (`true`). Long-running dev servers/watchers can be killed even when the model explicitly requested not to kill them.
- **Fix:** Forward `kill_on_timeout: toolCall.input.kill_on_timeout` in `handleCheckJob`, and add a handler-level unit test that verifies the full parsed schema input reaches the client tool call. Consider a typed helper or exhaustive input forwarding test for all pass-through client tools to prevent future schema/handler drift.
- **Evidence:** `common/src/tools/params/tool/check-job.ts:34-40` defines and documents `kill_on_timeout`. `sdk/src/tools/check-job.ts:33-40` accepts it and defaults `const killOnTimeout = params.kill_on_timeout ?? true`; `sdk/src/tools/check-job.ts:88` uses it before killing on timeout. But `packages/agent-runtime/src/tools/handlers/tool/check-job.ts:23-27` forwards only `jobId`, `wait_for`, and `timeout_seconds`.

## [MEDIUM] resource-lifecycle — `packages/agent-runtime/src/tools/tool-executor.ts:591` — AbortSignal is only pre-checked, not propagated to client tools or child processes
- **Risk:** Runtime handlers receive a `signal`, but client-tool execution only checks `params.signal.aborted` immediately before dispatch. Once a client tool starts, aborting the agent turn does not cancel a blocking `check_job` follow loop, a synchronous terminal command, or a ripgrep `code_search` process. Aborted turns can therefore leave expensive subprocesses or waits running until their own timeout, delaying cleanup and producing results for work the user already cancelled.
- **Fix:** Thread `AbortSignal` through the `requestToolCall` contract and SDK dispatch, and make client tools abort-aware: use `spawn(..., { signal })` where supported or attach an abort listener that kills the child; make polling sleeps abortable; return a cancellation-shaped tool result instead of waiting for normal timeout. Remove listeners in `finally`.
- **Evidence:** `packages/agent-runtime/src/tools/handlers/handler-function-type.ts:48` includes `signal: AbortSignal` in every handler param. `packages/agent-runtime/src/tools/tool-executor.ts:591-601` only does `if (params.signal.aborted) return []` before calling `requestToolCall({ userInputId, toolName, input })`; no signal is forwarded. `sdk/src/run.ts:827-899` dispatches `run_terminal_command`, `code_search`, `check_job`, `read_logs`, and `git_status` without any signal argument. `sdk/src/tools/run-terminal-command.ts:203-205` and `sdk/src/tools/code-search.ts:138-141` spawn child processes without an abort signal; `sdk/src/tools/check-job.ts:60-88` loops/sleeps until match, exit, or timeout with no abort check.

## [MEDIUM] security — `sdk/src/tools/code-search.ts:61` — `code_search.cwd` uses lexical prefix checks and can follow an in-project symlink outside the repo
- **Risk:** `code_search` validates `cwd` using `path.resolve` plus `startsWith(projectRoot + path.sep)`. That blocks obvious `..` traversal but not symlink traversal: if the repository contains a symlinked directory pointing outside the project, a caller can set `cwd` to that symlink and ripgrep will search the target outside the repo. This is inconsistent with the hardened file/path helpers and can leak arbitrary local file contents via search results.
- **Fix:** Validate `cwd` with realpath-aware containment (`resolveFilePathWithinProject`) before spawning ripgrep, or mirror `find_files_matching_content`'s lexical + realpath checks. Add a regression test where `cwd` is an in-project symlink to a temp directory outside the project.
- **Evidence:** `sdk/src/tools/code-search.ts:61-67` computes `projectRoot` and `searchCwd`, then only rejects when `!searchCwd.startsWith(projectRoot + path.sep) && searchCwd !== projectRoot`. `sdk/src/tools/code-search.ts:138-141` spawns ripgrep with `cwd: searchCwd`. The safer helper in `sdk/src/tools/path-utils.ts:53-82` verifies both lexical path and `realpath`; `sdk/src/tools/find-files-matching-content.ts:65-75` starts with a shared `isPathInside` guard and later performs realpath validation before searching.

## [MEDIUM] correctness — `sdk/src/tools/background-jobs.ts:421` — recovered shell jobs reset `readOffset` to zero, duplicating old output after restart
- **Risk:** `check_job` promises incremental output that never repeats across calls, but recovered background jobs are reconstructed with `readOffset: 0`. After a CLI/runtime restart, the next `check_job` for a recoverable job re-reads the entire log from byte zero. This can duplicate large logs, trigger `wait_for` on stale startup text, and make agents believe new output arrived when it was already consumed in the prior session.
- **Fix:** Persist the consumed offset in background-job metadata when `readNewJobOutput` advances it, and restore that offset on recovery. If cross-session incremental semantics are not intended, change the contract and return an explicit `recovered: true` / `offsetReset: true` marker so callers do not treat old log contents as new output.
- **Evidence:** `common/src/tools/params/tool/check-job.ts:52` states that output never repeats and each `check_job` advances the read offset. `sdk/src/tools/background-jobs.ts:14-21` repeats that the registry tracks `readOffset` so output is never duplicated or lost. `sdk/src/tools/background-jobs.ts:522-529` advances `job.readOffset` by bytes read. But `sdk/src/tools/background-jobs.ts:401-429` reconstructs a recovered job and sets `readOffset: 0` unconditionally.

## [LOW] correctness — `sdk/src/tools/glob.ts:34` — invalid `glob.cwd` silently broadens the search to the whole project
- **Risk:** The `glob` schema says `cwd` narrows the search scope, but when `cwd` resolves outside the project the SDK silently clears it and searches from the project root. A typo or traversal payload therefore returns a broader result set than requested rather than an error, which can mislead the agent into operating on unrelated files. This is not an outside-project leak, but it is inconsistent with `list_directory` and `code_search`, which return explicit invalid-path errors.
- **Fix:** Return a structured error for invalid `cwd` instead of dropping it. Keep `cwd` narrowing semantics fail-closed and add a regression test asserting `cwd: '../../outside'` does not broaden results.
- **Evidence:** `common/src/tools/params/tool/glob.ts:21-25` describes `cwd` as an optional working directory to search within. `sdk/src/tools/glob.ts:28-41` calls `resolveFilePathWithinProject`, but on failure executes `normalizedCwd = ''`; subsequent matching proceeds against the whole project tree. `sdk/src/tools/list-directory.ts:20-29` shows the safer pattern: return `Invalid path` when the resolved path is outside the project.

## Notes / non-findings
- File-changing handlers have a positive path-traversal guard: `packages/agent-runtime/src/tools/handlers/tool/write-file.ts:85-96` normalizes backslashes and rejects any `..` segment; `edit_transaction` blocks the whole transaction when normalization returns an empty path (`packages/agent-runtime/src/tools/handlers/tool/edit-transaction.ts:44-65`).
- `list.ts` is type-checked against `[K in ToolName]: CodebuffToolHandlerFunction<K>`, which reduces missing-handler drift, but it does not protect against per-field forwarding omissions like `check_job.kill_on_timeout`.
- Background-agent in-memory chunk offsets are bounded and adjusted on ring-buffer eviction (`packages/agent-runtime/src/util/background-agent-jobs.ts:173-182`, `210-216`); the offset-drift finding above is for shell background-job recovery across SDK/CLI process restarts.
